# Design Document: PWA Home Screen App

## Overview

This feature adds Progressive Web App (PWA) capabilities to the Go URL Alias Service, enabling users to install the app to their device home screen. When launched in standalone mode, the app presents a dedicated "Home Screen Page" — a minimal, focused interface with a tagline ("Where do you want to go today?"), the Go logo, and a single alias input field that navigates to `/{alias}` on submit.

The implementation uses `vite-plugin-pwa` to generate the web app manifest and service worker at build time, integrating cleanly with the existing Vite + React 18 + TypeScript stack. A standalone-mode detection mechanism (`window.matchMedia('(display-mode: standalone)')`) switches between the existing `LandingPage` and the new `HomeScreenPage` at the root route `/`.

## Architecture

```mermaid
graph TD
    subgraph Build Time
        V[vite.config.ts + vite-plugin-pwa] --> M[manifest.json]
        V --> SW[service-worker.js]
        V --> HTML[index.html with manifest link + meta tags]
    end

    subgraph Runtime - Root Route /
        A[App.tsx] --> D{isStandaloneMode?}
        D -->|Yes| HSP[HomeScreenPage]
        D -->|No| LP[LandingPage]
        HSP --> AI[Alias Input]
        AI -->|Submit| NAV[navigate to /{alias}]
        NAV --> AR[AliasRedirect catch-all]
    end

    subgraph Service Worker
        SW --> CACHE[Cache app shell]
        CACHE --> INSTALL[Enable install prompt]
    end
```

### Key Design Decisions

1. **`vite-plugin-pwa` over manual SW**: The plugin handles manifest generation, service worker creation, and HTML injection in one step. It's the standard approach for Vite apps and avoids maintaining a hand-rolled service worker.

2. **Standalone detection via `matchMedia`**: Using `window.matchMedia('(display-mode: standalone)')` is the standard, reliable way to detect if the app was launched from the home screen. This avoids URL query params or custom headers.

3. **Separate `HomeScreenPage` component**: Rather than conditionally rendering within `LandingPage`, a dedicated component keeps concerns clean. The route logic in `App.tsx` selects which component to render at `/`.

4. **Cache-first strategy for app shell only**: The service worker caches static assets (HTML, CSS, JS, icons) but does NOT cache API responses. Redirect requests (`/api/redirect/{alias}`) must always hit the network to ensure up-to-date URL resolution.

## Components and Interfaces

### New Components

#### `HomeScreenPage`
A standalone page rendered at `/` when the app is in standalone mode.

```typescript
// src/components/HomeScreenPage.tsx
interface HomeScreenPageProps {}

function HomeScreenPage(): JSX.Element
// - Displays Go logo (theme-aware via useTheme)
// - Displays tagline "Where do you want to go today?"
// - Renders AliasInput with submit handling
// - Navigates to `/${alias}` on submit
```

#### `useStandaloneMode` Hook
Detects whether the app is running in PWA standalone mode.

```typescript
// src/hooks/useStandaloneMode.ts
function useStandaloneMode(): boolean
// Returns true if display-mode is standalone or if iOS standalone flag is set
// Listens for matchMedia changes
```

### Modified Components

#### `App.tsx`
- Import `HomeScreenPage` and `useStandaloneMode`
- At the `/` route, conditionally render `HomeScreenPage` or `LandingPage` based on `isStandalone`
- When standalone, hide the app header (no nav bar needed in the focused home screen experience)

### Build Configuration

#### `vite.config.ts`
- Add `vite-plugin-pwa` plugin with configuration:
  - `registerType: 'autoUpdate'` — auto-update service worker on new builds
  - `manifest` object with name, icons, theme_color, background_color, display, start_url
  - `workbox.runtimeCaching` — cache-first for static assets, network-first for API calls

#### `index.html`
- Add `<meta name="theme-color">` tag
- Add `<meta name="apple-mobile-web-app-capable" content="yes">` tag
- Add `<link rel="apple-touch-icon">` referencing the 192x192 icon
- The `<link rel="manifest">` is injected automatically by `vite-plugin-pwa`

### Static Web App Config

#### `staticwebapp.config.json`
- Add routes for `/manifest.json` and `/sw.js` that allow anonymous access (no `allowedRoles` restriction)

## Data Models

No new data models are introduced. The feature operates entirely on the client side with existing browser APIs:

- **PWA Manifest** (`manifest.json`): Generated at build time by `vite-plugin-pwa`. Standard W3C Web App Manifest format.
- **Service Worker**: Generated by Workbox via `vite-plugin-pwa`. Manages cache storage using the Cache API.
- **Standalone mode detection**: Boolean derived from `window.matchMedia('(display-mode: standalone)')` and `navigator.standalone` (iOS Safari).

### Icon Assets

Two new PNG files in `public/`:
- `public/pwa-192x192.png` — 192×192 icon
- `public/pwa-512x512.png` — 512×512 icon

These are pre-generated from the existing `favicon.svg`.

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*

### Property 1: Alias submission navigates to correct path

*For any* non-empty, non-whitespace alias string, submitting the alias input on the HomeScreenPage SHALL produce a navigation to `/${alias}`.

**Validates: Requirements 3.4**

### Property 2: Empty or whitespace-only input disables submit

*For any* string composed entirely of whitespace characters (including the empty string), the submit action on the HomeScreenPage SHALL be disabled and no navigation SHALL occur.

**Validates: Requirements 3.5**

## Error Handling

| Scenario | Behavior |
|---|---|
| Service worker registration fails | Log error to `console.error`, app continues as normal web app (Req 2.3) |
| `matchMedia` not supported (old browser) | `useStandaloneMode` returns `false`, app falls back to LandingPage |
| `navigator.standalone` undefined (non-iOS) | Hook checks `matchMedia` only, returns appropriate boolean |
| User submits alias that doesn't exist | Existing `AliasRedirect` catch-all handles it — the redirect API returns 404 and the app shows the not-found page |
| Offline with cached shell | App shell loads from cache; alias submission will fail at the API redirect level since API calls are network-first |

## Testing Strategy

### Unit Tests (Example-Based)

- **HomeScreenPage rendering**: Verify tagline text, input field with placeholder, Go logo presence
- **Theme-aware logo**: Render with light and dark theme contexts, verify correct logo `src`
- **Standalone mode routing**: Mock `useStandaloneMode` to return `true`/`false`, verify correct component renders at `/`
- **Submit disabled when empty**: Verify submit button is disabled when input is empty
- **Submit navigates on valid input**: Type an alias, submit, verify `navigate` called with `/{alias}`
- **SW registration error handling**: Mock `navigator.serviceWorker.register` to reject, verify `console.error` called
- **SWA config**: Verify `staticwebapp.config.json` includes anonymous routes for `/manifest.json` and `/sw.js`

### Property-Based Tests

Property-based testing applies to the alias input validation and navigation logic — pure functions with clear input/output behavior across a large input space.

- **Library**: `fast-check` (already in devDependencies)
- **Minimum iterations**: 100 per property
- **Tag format**: `Feature: pwa-home-screen-app, Property {N}: {text}`

Each correctness property above maps to a single property-based test:

1. **Property 1 test**: Generate arbitrary non-empty trimmed strings, call the submit handler, assert navigation target is `/${alias}`
2. **Property 2 test**: Generate arbitrary whitespace-only strings (including empty), assert submit button is disabled / handler does not navigate

### What Is NOT Tested with PBT

- Manifest content (SMOKE — static config verification)
- Service worker caching behavior (INTEGRATION — browser/Workbox behavior)
- CSS layout and responsiveness (visual — not unit-testable)
- Icon file existence (asset check — not logic)
